## 二、前端基础与进阶（高频核心题）

### Q1：Vue2 和 Vue3 的核心差异？

**先说结论（15秒）**
Vue3 在响应式能力、逻辑组织和性能上都更适合中大型项目，尤其是 Composition API + TypeScript 的组合在可维护性上优势明显。

**标准答案（60秒）**
1. 响应式层：Vue2 主要基于 `Object.defineProperty`，Vue3 基于 `Proxy`，对新增属性、数组下标和深层对象监听更自然。
2. 代码组织：Vue2 的 Options API 在复杂组件中容易逻辑分散；Vue3 的 Composition API 可以按“业务能力”聚合逻辑，复用时用 composables，避免 mixin 污染。
3. 性能机制：Vue3 编译期优化（静态提升、PatchFlag 等）更充分，运行时更轻，Tree Shaking 更友好。
4. 工程协作：Vue3 + TS 类型推导更完整，重构风险更低，团队协作更稳定。

**追问准备**
如果面试官问“你们有没有迁移成本”，你答：
- 成本主要在生态兼容、团队心智迁移和历史组件改造。
- 迁移策略是“新业务先 Vue3，旧模块渐进替换”，不做一刀切。

**结合你项目的话术**
海外版项目从 0 到 1 我直接选 Vue3 + Vite + TS，核心原因就是后续多语言、多币种、跨区域规则复杂，必须保证长期可维护性。

**避坑点**
不要只说“Vue3 更快”，要说“为什么更快、对业务有什么价值”。

---

### Q2：Composition API 的价值是什么？

**结论**
它解决的不是“语法新旧”，而是复杂业务的“逻辑可组合、可复用、可测试”。

**标准答案**
1. 按领域能力组织代码：比如 `useTenantList`、`useBillFilters`，而不是把同一个功能拆散在 data/watch/method。
2. 复用模式更稳：composable 比 mixin 更可控，参数和返回值清晰。
3. 类型链路更完整：组合函数天然适合 TS，接口变更能在编译阶段暴露。
4. 测试友好：逻辑函数可脱离 UI 做单元测试。

**项目话术**
在跨端和海外版里，我把筛选、分页、字典映射、权限控制都做成 composable，降低页面重复逻辑。

### Q3：Pinia 和 Vuex 的取舍？

**结论**
Pinia 更轻、更自然、更适合 Vue3 + TS；Vuex 在老项目和历史沉淀里仍有价值。

**标准答案**
1. Pinia 去掉 mutation 层，开发心智更直接。
2. TS 支持显著更好，类型推导顺滑。
3. 模块组织更自由，store 更贴近业务域。
4. 迁移时要考虑老项目插件和中间件依赖，不要硬迁。

**你可加一句**
我做过 Vuex 大仓拆分和 Pinia 体系搭建，核心原则都是“按业务域拆、按稳定接口连”。

### Q4：你如何做前端性能优化？

**结论**
性能优化不是“只调一个点”，而是“构建、加载、渲染、交互、监控”全链路治理。

**标准答案（结构化）**
1. 构建层：拆包、压缩、去冗余依赖、CDN 分发。
2. 加载层：路由懒加载、组件按需、关键资源优先、非关键延迟。
3. 渲染层：虚拟列表、减少重排重绘、图表增量更新。
4. 交互层：防抖节流、请求合并、缓存策略、keep-alive。
5. 监控层：定义首屏/FCP/LCP/TTI 指标，防止优化回退。

**项目结果**
全房通 SaaS：首屏 4.2s -> 2.1s，交互提升约 30%。

**追问准备：怎么定位瓶颈？**
- Lighthouse 看全局问题。
- Performance 面板看长任务和渲染耗时。
- Network 看大资源和阻塞链路。
- Bundle 分析看包体积和重复依赖。

### Q5：Webpack 和 Vite 在实战中的差异？

**结论**
Vite 在开发体验上优势很大，Webpack 在复杂历史生态里更稳，选型看项目阶段。

**标准答案**
1. 开发模式：Webpack 先打包再启动；Vite 基于 ESM 按需加载，冷启动快。
2. HMR：Vite 热更新链路更短，体感更快。
3. 构建：Vite 通常基于 Rollup，配置更轻，但复杂定制时也要评估插件生态。
4. 迁移策略：老系统建议“增量迁移”，先抽公共包再切核心模块。

**你的项目数据**
海外版项目通过 Vite 依赖预构建 + 拆包 + 缓存策略，把热更新时间压到 200ms 内。

### Q6：浏览器渲染机制怎么讲才像高级？

**结论**
核心是减少主线程压力，降低 layout/paint 成本，把高频动画交给合成层。

**标准答案**
1. 解析：HTML -> DOM，CSS -> CSSOM。
2. 构建：Render Tree。
3. 布局与绘制：Layout -> Paint -> Composite。
4. 优化：避免频繁读取布局属性导致强制同步布局；动画优先 `transform/opacity`；减少大面积阴影和滤镜。

**追问：为什么页面会“偶尔卡住”？**
- JS 长任务阻塞主线程。
- 微任务队列过长。
- 大量同步渲染/重排。

### Q7：你如何设计可扩展的前端工程结构？

**结论**
工程结构先服务团队协作，再服务技术偏好。

**标准答案**
1. 目录按领域划分：`apps/modules/shared` 或 `views/components/composables/services`。
2. 请求层、权限层、字典层、国际化层独立。
3. 组件分层：基础组件 -> 业务组件 -> 页面编排。
4. 规范落地：ESLint + 提交流程 + PR 模板 + 文档。

**你可补充**
我做海外版从 0 到 1 时，第一周先定目录、路由、状态、请求封装和权限基线，再并行开发业务。

### Q8：你怎么做前端错误治理？

**标准答案**
1. 错误分类：资源加载错误、运行时错误、接口错误、Promise 未捕获。
2. 统一采集：全局 error/rejection + 接口拦截。
3. 上报字段：traceId、用户、页面、设备、版本、操作路径。
4. 闭环机制：按严重度分级，回归用例沉淀。

**面试加分句**
“错误上报不是为了统计，而是为了缩短定位路径和提升修复 SLA。”

### Q10：Spring Boot 接口怎么设计更利于前端？

**标准答案**
1. 统一响应结构：`code/message/data/traceId`。
2. 分页结构统一：`list/total/pageNo/pageSize`。
3. 枚举和状态字段明确语义，避免魔法值。
4. 字段命名稳定，版本升级保持向后兼容。

**避坑点**
不要让不同接口返回风格不同，否则前端封装会被迫碎片化。

---

### Q11：如何处理接口幂等和重复提交？

**标准答案**
1. 前端：按钮 loading + 防抖 + 提交态锁。
2. 后端：幂等 token 或唯一业务键。
3. 缓存层：Redis 做短时间防重。
4. 数据层：唯一索引兜底。

### Q12：MySQL 性能问题怎么回答？

**结论**
高级回答要讲“定位过程”，不是只背“建索引”。

**标准答案**
1. 先用 `explain` 看执行计划。
2. 判断是否走索引、是否回表、是否 filesort。
3. 调整索引顺序（最左前缀）和 SQL 写法。
4. 大结果集分页优化（避免深分页）。

**你可说**
联调中遇到慢查询我会和后端一起看执行计划，不只停留在前端层。

### Q16：你把首屏 4.2s 优化到 2.1s，具体做了什么？

**标准答案（分步）**
1. 先测量：通过性能面板和资源瀑布图找大头资源与阻塞链路。
2. 再拆包：路由级别懒加载，重组件按需引入。

4. 再治理：图片懒加载、接口并发控制、预加载关键资源。
5. 再验证：回归核心页面，观察线上指标是否稳定。

**可量化结果**
首屏加载 4.2s -> 2.1s，交互响应约 +30%。

## 十、答题模板（万能）

### 模板1：技术实现题
我先说结论：我会优先保证可维护性和稳定性。具体分三步：第一步……第二步……第三步……最终结果是……

### 模板2：项目复盘题
这个项目的核心挑战是……我负责……采取了……最终把……从……提升到……这次复盘我沉淀了……

### 模板3：不会的题
这个场景我没有完全一致的项目经历，但我做过相似问题。我的处理思路是先最小复现，再定位瓶颈，再分层修复并验证回归。

---

## 十一、最终提醒（面试表现）

1. 每题先说结论，不要先铺背景。
2. 每题尽量带一个数据结果（时间、比例、效率）。
3. 少讲“我会”，多讲“我做过”。
4. 不和面试官争对错，强调“取舍依据和业务约束”。
5. 不会时别硬扛，用“相似经验 + 解决路径”拿分。

> 你的经历非常适配“高级前端 + 全链路协同”岗位。面试关键不是背更多，而是把“可量化结果 + 结构化表达”稳定输出。
