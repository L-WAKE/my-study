## 四、前端基础高频题

### Q1：事件循环怎么理解？

答：

> JavaScript 是单线程执行的，事件循环负责协调同步任务、微任务和宏任务。同步代码先执行，遇到异步任务会交给宿主环境处理。当前调用栈清空后，会先清空微任务队列，再执行一个宏任务，然后继续循环。
>
> 常见微任务有 Promise.then、MutationObserver、queueMicrotask；常见宏任务有 setTimeout、setInterval、I/O、UI 事件。面试里重点记住：同步代码先执行，微任务优先于下一个宏任务。

速记：

> 同步先走，微任务清空，再宏任务循环。

### Q2：Promise、async/await 的关系？

答：

> async/await 是 Promise 的语法糖。async 函数一定返回 Promise，await 后面如果是 Promise，会等待它变成 fulfilled 或 rejected；如果是普通值，会包装成 resolved Promise。
>
> await 后面的代码可以理解为放到微任务里执行，所以它不会阻塞整个线程，只是让当前 async 函数后续逻辑等待异步结果。

速记：

> async 返回 Promise，await 等结果，本质还是微任务。

### Q3：闭包是什么？项目中怎么用？

答：

> 闭包是函数可以访问它定义时所在词法作用域中的变量，即使外层函数已经执行完，这些变量仍然能被内部函数引用。
>
> 项目里常见场景有防抖节流、模块私有变量、缓存函数、函数柯里化等。比如防抖函数通过闭包保存 timer，每次触发时清除上一次定时器，从而控制高频事件的执行次数。

速记：

> 函数记住定义时的作用域。常用于防抖、节流、缓存、私有变量。

### Q4：防抖和节流区别？

答：

> 防抖是高频触发后只执行最后一次，适合搜索框输入、窗口 resize 后再计算。节流是一段时间内最多执行一次，适合滚动监听、拖拽、按钮连续点击限制。
>
> 简单说，防抖关注“停下来再执行”，节流关注“固定频率执行”。

速记：

> 防抖等最后，节流控频率。

### Q5：深拷贝要注意什么？

答：

> 简单对象可以用 JSON.parse(JSON.stringify())，但它会丢失 undefined、function、Symbol、Date、RegExp、Map、Set，也处理不了循环引用。
>
> 更完整的深拷贝要考虑类型判断、循环引用、特殊对象和原型。现代浏览器可以使用 structuredClone，但也要注意函数、DOM 节点等不可克隆对象。

速记：

> JSON 方案简单但有坑，完整方案要处理类型、循环引用、特殊对象。

### Q6：浏览器从输入 URL 到页面展示发生了什么？

答：

> 大致流程是 DNS 解析、建立 TCP 连接、HTTPS 还会 TLS 握手、发送 HTTP 请求、服务器响应资源、浏览器解析 HTML，构建 DOM 和 CSSOM，合成 Render Tree，进行布局、绘制和合成，最后展示页面。
>
> 性能优化也可以对应这些阶段，比如 DNS 预解析、CDN、缓存、压缩、减少阻塞资源、代码分割、图片懒加载和减少重排重绘。

速记：

> DNS、连接、请求、响应、解析、布局、绘制、合成。

### Q7：重排和重绘区别？

答：

> 重排是元素几何信息发生变化，比如宽高、位置、display、字体大小变化，需要重新计算布局。重绘是视觉样式变化，比如颜色、背景色变化，不一定影响布局。
>
> 重排成本通常高于重绘。优化方式包括批量修改 DOM、使用 class 一次性更新样式、避免频繁读取和写入布局属性、动画优先使用 transform 和 opacity。

速记：

> 布局变是重排，颜色变是重绘；动画尽量 transform / opacity。

### Q8：localStorage、sessionStorage、cookie 区别？

答：

> cookie 会随请求发送到服务端，容量小，适合存 token 标识但要注意安全属性。localStorage 容量相对大，持久保存，除非主动清除。sessionStorage 只在当前会话窗口有效，关闭页面后清除。
>
> 对安全要求高的 token，不能简单只看存哪里，还要配合 HTTPS、HttpOnly、SameSite、过期机制和后端校验策略。

速记：

> cookie 随请求，localStorage 持久，sessionStorage 会话级。

### Q9：前端安全常见问题有哪些？

答：

> 常见有 XSS、CSRF、点击劫持、接口越权、敏感信息泄露、依赖包风险。
>
> XSS 防护重点是输入校验、输出转义、避免 v-html 直接渲染不可信内容、CSP。CSRF 防护可以用 SameSite Cookie、CSRF Token、Referer / Origin 校验。权限问题不能只依赖前端按钮隐藏，后端必须做权限校验。

速记：

> XSS 防注入，CSRF 防伪造，权限后端兜底。

### Q10：跨域是什么？怎么解决？

答：

> 跨域是浏览器同源策略限制，不同协议、域名、端口之间的请求会受到限制。常用解决方案是后端配置 CORS、开发环境代理、Nginx 反向代理，特殊场景也有 JSONP，但现在较少使用。
>
> 实际项目里开发环境我通常用 Vite 或 Webpack devServer proxy，生产环境一般由 Nginx 或后端网关处理 CORS。

速记：

> 开发用 proxy，生产用 Nginx / 网关 / CORS。

## 五、Vue 高频题

### Q1：Vue2 和 Vue3 响应式区别？

答：

> Vue2 主要基于 Object.defineProperty 对对象属性做 getter / setter 拦截，所以对新增属性、数组下标修改等场景有局限，需要 Vue.set 等方式处理。
>
> Vue3 基于 Proxy，可以直接代理整个对象，能更自然地监听新增、删除、数组、Map、Set 等变化，响应式能力更完整。同时 Vue3 配合 Composition API，让逻辑复用和大型组件拆分更灵活。

速记：

> Vue2 defineProperty 拦属性，Vue3 Proxy 拦对象。

### Q2：Composition API 相比 Options API 优势？

答：

> Options API 按 data、methods、computed、watch 分类，简单页面很清晰，但复杂组件中同一业务逻辑会分散在多个选项里。Composition API 可以按业务逻辑组织代码，把相关状态、方法、副作用放在一起，并且更适合封装 composable。
>
> 在海外版和移动端项目里，我用 Composition API 抽象了表单、列表、权限、字典、请求等逻辑，提高了复用性和可维护性。

速记：

> Options 按类型分，Composition 按业务逻辑聚合，更适合复杂组件复用。

### Q3：Vue 中 computed 和 watch 区别？

答：

> computed 适合根据已有状态派生新值，有缓存，依赖不变不会重新计算。watch 适合监听数据变化后执行副作用，比如请求接口、写缓存、触发表单校验。
>
> 简单说，需要一个“值”用 computed，需要“做一件事”用 watch。

速记：

> computed 要结果，watch 做动作。

### Q4：Vue key 的作用？

答：

> key 用于帮助虚拟 DOM diff 识别节点身份。如果列表没有稳定 key，Vue 可能复用错误节点，导致表单输入、组件状态、动画出现异常。
>
> 实际项目里我会优先用业务唯一 id，不建议用 index 作为动态列表 key，除非列表完全静态且不会增删排序。

速记：

> key 是节点身份证，动态列表不要随便用 index。

### Q5：Vue 组件通信方式有哪些？

答：

> 父子组件可以用 props 和 emit；跨层级可以用 provide / inject；全局状态用 Vuex 或 Pinia；兄弟组件可以通过共同父组件、状态管理或事件总线，但 Vue3 里一般不推荐滥用 event bus。
>
> 项目中我更倾向于局部状态放组件内部，跨模块共享状态放 Pinia / Vuex，权限、字典、用户信息等放全局 Store。

速记：

> 父子 props/emit，跨层 provide/inject，全局 Pinia/Vuex。

### Q6：Vuex 和 Pinia 区别？

答：

> Vuex 更偏传统集中式状态管理，有 state、mutations、actions、getters。Pinia API 更简洁，没有 mutations，天然支持 TypeScript，组合式写法更友好，模块拆分也更自然。
>
> 在 Vue2 老项目里我做过 Vuex Store 拆分；在 Vue3 海外版和移动端里，我更倾向用 Pinia 管理用户信息、权限、字典、业务缓存等状态。

速记：

> Vuex 重规范，Pinia 更轻、更适合 Vue3 和 TS。

### Q7：keep-alive 的作用和注意点？

答：

> keep-alive 用于缓存组件实例，避免组件频繁销毁和重建，适合列表页返回保留查询条件、滚动位置、已加载数据等场景。
>
> 注意不要滥用，否则会导致内存占用增加、数据不刷新。需要结合 activated、deactivated 生命周期处理刷新策略和缓存清理。

速记：

> 缓存组件保状态，但要控制刷新和内存。

### Q8：Vue 项目权限怎么设计？

答：

> 一般分菜单权限、路由权限、按钮权限和接口权限。前端根据登录后的用户角色或权限码动态生成路由和菜单，按钮通过指令或组件控制展示，接口权限必须由后端兜底。
>
> 我的项目里通常会把用户信息、权限码、菜单树放到 Store；路由守卫里处理登录校验、动态路由加载和页面访问控制；按钮权限通过自定义指令或权限组件统一处理。

速记：

> 菜单、路由、按钮前端控制，接口权限后端兜底。

### Q9：Vue 表单很多字段怎么维护？

答：

> 我会优先做配置化和组件化。比如把字段 label、prop、组件类型、校验规则、字典、显隐条件、联动逻辑抽象成配置，再由统一的 FormRenderer 渲染。
>
> 复杂逻辑不能全部塞进配置，否则可读性会下降。我的原则是通用结构配置化，复杂业务逻辑保留代码表达，两者结合。

速记：

> 通用字段配置化，复杂逻辑代码化。

### Q10：如何封装一个好组件？

答：

> 我会从 API 稳定性、业务边界、可扩展性、默认行为、插槽、事件、类型定义和文档几个方面考虑。组件不应该知道太多业务细节，应该通过 props、emit、slots 暴露扩展点。
>
> 在 Uniapp 项目中，我封装过弹窗、JSON 表单、筛选、权限按钮等组件，并用 VitePress 写 API、示例和最佳实践，降低团队接入成本。

速记：

> 边界清晰、API 稳定、插槽扩展、类型完整、文档跟上。

## 六、TypeScript 高频题

### Q1：为什么项目要用 TypeScript？

答：

> TypeScript 最大价值是把一部分运行时错误提前到编译期发现，尤其适合多人协作、接口字段多、业务模型复杂的中后台项目。
>
> 在海外版项目里，我用 TS 建立接口类型、表单模型、枚举配置和数据转换逻辑，减少字段变更导致的联调问题，也让组件 props、emit 和业务数据更清晰。

速记：

> TS 让错误提前暴露，让接口、组件、业务模型更可维护。

### Q2：interface 和 type 区别？

答：

> interface 更适合描述对象结构，可以声明合并和扩展；type 更灵活，可以定义联合类型、交叉类型、工具类型、函数类型等。
>
> 我的习惯是业务对象、接口响应优先 interface，复杂联合、工具类型、字面量类型用 type。

速记：

> 对象结构 interface，复杂组合 type。

### Q3：泛型有什么用？

答：

> 泛型用于在定义函数、接口、类时保留类型参数，让代码既复用又不丢类型。比如请求封装可以写成 request<T>()，调用时指定返回数据类型，后续使用 data 时就能获得类型提示。
>
> 它解决的是“类型也要参数化”的问题。

速记：

> 泛型就是类型参数，让复用代码保留类型信息。

### Q4：如何给后端接口做类型管理？

答：

> 我会按业务模块维护 request、response、query、form、enum 等类型。接口请求函数用泛型绑定响应类型，页面层尽量不要直接写 any。
>
> 如果后端有 Swagger / OpenAPI，也可以结合工具或 AI 生成基础类型，再人工校验关键字段，避免前后端字段理解不一致。

速记：

> 按模块管入参出参，request 泛型绑定响应，减少 any。

## 七、工程化 / 构建高频题

### Q1：Webpack 和 Vite 的区别？

答：

> Webpack 是传统打包器，开发时也会先构建依赖图再启动，生态成熟，适合复杂老项目。Vite 开发环境基于原生 ESM，启动时不需要把所有业务代码都打包，依赖预构建用 esbuild，所以冷启动和热更新更快；生产构建通常基于 Rollup。
>
> 在老 Vue2 项目里我优化过 Webpack 拆包和缓存；在 Vue3 海外版里用 Vite 把热更新时间优化到 200ms 以内。

速记：

> Webpack 生态成熟但重，Vite 开发快，基于 ESM + esbuild + Rollup。

### Q2：Vite 为什么快？

答：

> Vite 快主要有两个原因。第一，开发环境利用浏览器原生 ESM，按需加载源码，不需要启动时全量打包。第二，依赖预构建使用 esbuild，速度比传统 JS 打包器更快。
>
> 热更新时 Vite 可以精确更新变更模块，不需要重新构建整个应用，所以大型项目体验更好。

速记：

> 原生 ESM 按需加载，esbuild 预构建，HMR 精准更新。

### Q3：Webpack 性能优化做过哪些？

答：

> 我做过代码分割、路由懒加载、第三方库拆包、缓存策略、CDN 外链、按需加载、压缩和 Bundle 分析。开发阶段可以优化 loader 范围、开启缓存、减少不必要插件。
>
> 线上优化关注包体积和缓存命中，构建优化关注编译速度。两者目标不完全一样，需要分开看。

速记：

> 线上看体积缓存，开发看编译速度。

### Q4：前端项目规范怎么落地？

答：

> 我会从 ESLint、Prettier、TypeScript、提交规范、目录规范、组件规范、接口规范和 Code Review 几方面落地。规范不能只写文档，必须接入工程流程，比如保存自动格式化、提交前检查、CI 检查。
>
> 这两年我还会结合 AI 做代码审查，辅助识别重复逻辑、潜在空值、命名不一致和边界场景遗漏。

速记：

> 规范要进流程：本地检查、提交检查、CI、Code Review、AI 辅助。

### Q5：如何设计请求封装？

答：

> 请求封装一般包括 baseURL、timeout、请求头、token 注入、统一响应结构、错误码处理、登录过期处理、重复请求控制、loading、消息提示和文件上传下载等。
>
> 我会把底层 axios 实例、业务 API 函数和页面调用分层，页面不要直接拼 URL，避免接口散落难维护。

速记：

> axios 实例、拦截器、错误码、token、API 分层。

### Q6：如何做前端错误监控？

答：

> 可以从 JS 运行时错误、Promise 未捕获错误、资源加载错误、接口错误、框架错误钩子和性能指标几方面采集。Vue 项目可以用 errorHandler，浏览器层用 window.onerror 和 unhandledrejection。
>
> 采集后要带上用户、路由、版本、浏览器、接口、错误栈等上下文，方便定位。只收集错误不分析没有意义，还要建立告警和复盘机制。

速记：

> 收集错误、带上下文、能告警、能复盘。

## 八、性能优化专项

### Q1：你如何系统性做性能优化？

答：

> 我会分四步：第一，建立指标，比如 FCP、LCP、TTI、接口耗时、包体积、首屏时间。第二，用 Performance、Network、Lighthouse、Bundle Analyzer 定位瓶颈。第三，按加载、渲染、网络、缓存、代码执行分别优化。第四，上线后对比数据，确认收益。
>
> 我不建议一上来就盲目优化，因为性能问题可能来自包体积、接口慢、图片大、组件渲染多、缓存差，必须先定位。

速记：

> 定指标、找瓶颈、分层优化、数据验证。

### Q2：首屏优化有哪些手段？

答：

> 常见有路由懒加载、组件懒加载、第三方库拆包、CDN、资源压缩、图片优化、骨架屏、缓存、预加载关键资源、减少阻塞 CSS / JS、接口合并或并行请求。
>
> 中后台项目里，我最常用的是路由拆分、按需加载、静态资源缓存和减少首屏不必要接口。

速记：

> 拆包、懒加载、压缩、缓存、CDN、减少首屏请求。

### Q3：大列表性能怎么优化？

答：

> 如果数据量大，首先考虑分页、服务端筛选和虚拟列表，不要一次性渲染几万条 DOM。其次减少行组件复杂度，避免每行都创建大量响应式对象和复杂计算。
>
> 对于表格类页面，还可以做列配置缓存、防抖筛选、接口分页、局部更新和合理使用 loading。

速记：

> 分页优先，必要时虚拟列表，减少 DOM 和响应式开销。

### Q4：ECharts 大屏怎么优化？

答：

> ECharts 优化可以从数据量、渲染频率、图表实例管理和资源加载入手。比如控制数据点数量、使用 progressive / large 模式、避免频繁 setOption 全量更新、页面销毁时 dispose 实例。
>
> 大屏项目里还要关注图片、视频、地图 JSON 体积，以及长时间运行的内存泄漏问题。

速记：

> 控数据量、控更新频率、dispose 实例、防内存泄漏。

## 九、Java / Spring Boot / MySQL 高频题

### Q1：你 Java 后端能力到什么程度？

答：

> 我的主方向还是高级前端，但这两年在项目中参与了 Java / Spring Boot / MySQL / Redis 的后端开发。我能理解 Controller、Service、Mapper / DAO 的分层，能写业务接口、参数校验、SQL 查询、字段映射、统一响应、异常处理，也能参与前后端联调和问题定位。
>
> 但我会客观表达，我不是以高并发架构或 JVM 底层调优为主的纯后端专家。我的优势是前端经验深，加上后端基础和 AI 工具，能快速补齐业务闭环，减少联调沟通成本。

速记：

> 主前端，懂后端分层，能写业务接口和 SQL，能联调闭环，不包装成纯后端专家。

### Q2：Spring Boot 一个接口从请求到返回的流程？

答：

> 请求先进入网关或服务，Spring MVC 根据路由匹配 Controller 方法，Controller 做参数接收和基础校验，然后调用 Service 处理业务逻辑，Service 再调用 Mapper / DAO 操作数据库，最后返回统一响应结构。
>
> 实际项目中还会经过拦截器、过滤器、权限校验、异常处理、日志记录等环节。

速记：

> Controller 接参，Service 业务，Mapper 查库，统一响应返回。

### Q3：Controller、Service、Mapper 分别负责什么？

答：

> Controller 负责接收请求、参数校验和返回响应，不应该写复杂业务逻辑。Service 负责业务编排、事务控制和核心规则。Mapper / DAO 负责数据库访问和 SQL 映射。
>
> 分层的目的是降低耦合，让接口层、业务层、数据层职责清晰，后续维护和测试更容易。

速记：

> Controller 管入口，Service 管业务，Mapper 管数据库。

### Q4：什么是统一响应结构？

答：

> 统一响应结构通常包含 code、message、data，有时还会包含 traceId、timestamp。它的好处是前端可以统一处理成功、失败、登录过期、权限不足和业务错误。
>
> 前后端联调时，统一响应结构非常重要，否则每个接口返回格式不一致，前端错误处理会很混乱。

速记：

> code、message、data，方便前端统一处理。

### Q5：如何设计接口？

答：

> 我会关注 URL 语义、请求方法、参数结构、响应结构、错误码、权限、幂等性和兼容性。比如查询用 GET，新增用 POST，修改用 PUT / PATCH，删除用 DELETE，实际也要结合团队规范。
>
> 对前端来说，接口设计最重要的是字段语义清晰、结构稳定、错误码明确，避免一个字段在不同场景含义不同。

速记：

> URL 语义清晰，参数响应稳定，错误码明确，权限后端兜底。

### Q6：MySQL 索引是什么？为什么能加速？

答：

> 索引可以理解为数据库为字段建立的有序数据结构，常见 InnoDB 使用 B+ 树。没有索引时可能全表扫描，有索引时可以快速定位数据范围，减少扫描行数。
>
> 但索引不是越多越好，因为写入、更新、删除时也要维护索引，会增加成本。要根据查询条件、排序、关联字段合理设计。

速记：

> 索引减少扫描，但会增加写入维护成本。

### Q7：什么情况下索引会失效？

答：

> 常见情况包括对索引列使用函数或计算、like 以百分号开头、隐式类型转换、联合索引不满足最左前缀、or 条件使用不当、范围查询后面的列无法充分利用索引等。
>
> 实际排查时要看 explain，关注 type、key、rows、Extra 等信息。

速记：

> 函数计算、左模糊、类型转换、不满足最左前缀，都可能失效。

### Q8：Redis 在项目中怎么用？

答：

> Redis 常用于缓存热点数据、登录 token、验证码、分布式锁、计数器等。我的项目里更多是理解和联调缓存逻辑，比如字典、权限、用户会话或部分业务查询结果。
>
> 使用 Redis 要注意缓存穿透、击穿、雪崩，以及数据一致性问题。常见解决方案包括空值缓存、布隆过滤器、互斥锁、随机过期时间和主动更新缓存。

速记：

> Redis 做缓存和会话，注意穿透、击穿、雪崩、一致性。

### Q9：什么是事务？

答：

> 事务用于保证一组数据库操作要么全部成功，要么全部失败。它有 ACID 特性：原子性、一致性、隔离性、持久性。
>
> 在业务上，比如账单生成、合同状态变更、付款记录写入这类操作，如果中间任何一步失败，就不能只保存一部分数据，需要事务回滚。

速记：

> 一组操作同生共死，失败回滚。

### Q10：如何排查接口慢？

答：

> 我会先区分是前端慢、网络慢、网关慢、后端业务慢还是数据库慢。前端看 Network 的 waiting、download、接口耗时；后端看日志耗时；数据库看 SQL、索引、执行计划。
>
> 常见原因有 SQL 没索引、返回数据太大、循环调用接口、后端串行处理、缓存未命中、网络环境差。排查思路是分段打点，不要凭感觉猜。

速记：

> 分段定位：前端、网络、后端、数据库。用日志和耗时说话。

## 十、AI 工具使用高频题

### Q1：你说用 AI 做开发，具体怎么用？

答：

> 我主要把 AI 用在六类场景：需求拆解、代码生成、Bug 定位、重构优化、测试用例生成、技术文档沉淀。
>
> 比如海外版项目里，我用 AI 辅助多语言文案翻译、字段命名、TypeScript 类型生成；工程化优化里，用 AI 分析 Webpack / Vite 配置和包体积；后端开发里，用 AI 辅助生成 Spring Boot 接口、SQL 草稿和异常处理，但关键业务逻辑、权限、数据一致性和安全问题一定人工复核。

速记：

> AI 做提效，不做甩锅；生成可参考，关键要复核。

### Q2：AI 生成代码你怎么保证质量？

答：

> 我不会直接复制上线。一般会先明确上下文和约束，让 AI 生成初稿，然后我做人工 Review，重点检查业务逻辑、边界条件、类型、异常处理、权限、安全和性能。之后再通过本地运行、测试用例、ESLint / TypeScript 检查和 Code Review 验证。
>
> AI 更像一个高级助手，可以提高起步速度，但工程质量还是要靠开发者负责。

速记：

> 明确约束、人工 Review、测试验证、责任在人。

### Q3：AI 在团队流程里怎么落地？

答：

> 我认为 AI 最适合接入重复性、规则性、文档性和辅助分析类流程。比如生成组件文档、补充测试场景、做代码 Review 清单、分析构建配置、整理接口字段说明。
>
> 在团队里要建立规范，比如哪些代码可以让 AI 辅助生成，哪些敏感信息不能输入，生成内容必须经过 Review，不能把密钥、客户数据、生产日志直接给外部模型。

速记：

> 用在重复和辅助分析，敏感信息不外传，生成内容必须 Review。

### Q4：面试官质疑“AI 开发是不是你自己能力不够”怎么答？

答：

> 我会这样理解：AI 不能替代工程判断，反而会放大开发者的能力差异。没有基础的人可能无法判断 AI 代码对不对，而有经验的人可以用 AI 更快完成方案比较、重复代码生成、边界场景补充和文档沉淀。
>
> 我的核心能力还是前端架构、组件设计、性能优化和复杂业务理解。AI 是提效工具，不是能力替代品。

速记：

> AI 放大能力，不替代判断。基础越强，用 AI 越稳。

### Q5：AI 写后端接口时你关注什么？

答：

> 我会重点关注接口语义、参数校验、权限校验、事务、异常处理、SQL 是否合理、字段映射是否准确、返回结构是否统一，以及有没有安全风险。
>
> 对 AI 生成的 SQL，我会结合表结构、索引和 explain 思路检查，不会直接相信。

速记：

> 看参数、权限、事务、异常、SQL、返回结构、安全。

## 十一、项目管理 / 高级前端能力

### Q1：高级前端和普通前端区别是什么？

答：

> 普通前端更多关注单个需求能不能完成；高级前端除了完成需求，还要关注架构设计、工程规范、组件复用、性能、可维护性、团队协作和风险控制。
>
> 比如同样做一个表单，普通做法是页面写完；高级前端会考虑字段配置、校验复用、权限控制、接口类型、异常状态、后续扩展和团队接入成本。

速记：

> 不只写页面，还要考虑长期维护和团队效率。

### Q2：你如何推动团队规范？

答：

> 我会先从痛点切入，不会一上来定很多没人执行的规则。比如重复代码多，就推动组件封装；格式不统一，就接 ESLint / Prettier；接口联调混乱，就定统一响应和字段规范；组件没人会用，就补 VitePress 文档。
>
> 规范要尽量工具化、自动化、文档化，否则靠口头约定很难长期坚持。

速记：

> 从痛点出发，规范工具化、自动化、文档化。

### Q3：需求很急但质量有风险怎么办？

答：

> 我会先和产品、测试、后端明确优先级，把核心链路和可延期项拆开。对于必须上线的功能，保证主流程、权限、安全、数据正确性和异常兜底；对于体验优化、非核心配置可以分阶段交付。
>
> 同时要把风险透明化，而不是自己硬扛。上线后补充技术债清单，避免临时方案长期存在。

速记：

> 保核心链路，拆延期项，风险透明，上线后还债。

### Q4：遇到线上 Bug 怎么处理？

答：

> 我会先止血，再定位，再复盘。止血包括回滚、降级、临时开关或快速修复；定位要收集用户、时间、版本、路由、接口、日志、错误栈；修复后要补测试和监控，复盘根因，防止重复发生。

速记：

> 先止血，再定位，修复后复盘。

### Q5：你怎么和后端协作？

答：

> 我会尽量提前参与接口设计，明确字段含义、数据结构、错误码、分页、排序、权限和边界场景。开发中通过 Mock 或联调环境并行推进，遇到问题用具体请求参数、响应、日志和截图沟通。
>
> 因为我也懂一些 Java / Spring Boot / MySQL，所以很多问题能先判断是前端展示、参数传递、接口逻辑还是 SQL 数据问题，沟通效率会更高。

速记：

> 提前定接口，联调用证据，能判断问题在哪一层。

## 十二、场景题速答

### Q1：一个页面越来越慢，你怎么排查？

答：

> 先确认慢在哪里，是首屏加载慢、接口慢、渲染慢、操作卡顿还是内存泄漏。然后用 Network 看资源和接口，用 Performance 看长任务和渲染，用 Vue Devtools 看组件更新，用 Bundle Analyzer 看包体积。
>
> 根据结果分别处理，比如接口慢查 SQL 和缓存，包大做拆包和懒加载，渲染慢减少响应式数据和 DOM，操作卡顿做防抖节流或虚拟列表。

### Q2：表单字段非常多而且经常变化，怎么设计？

答：

> 我会做配置化表单，把字段、组件类型、校验、默认值、显隐、联动、字典、布局抽象成配置。后端如果也参与配置，需要约定 schema。
>
> 但复杂业务逻辑不要全部塞配置里，否则会变成另一套难维护的 DSL。我的原则是通用字段配置化，复杂逻辑代码化。

### Q3：多语言项目怎么设计？

答：

> 基础是语言包和 i18n 插件，但实际项目还要考虑日期格式、金额格式、币种、数字精度、枚举字段、表单校验文案、接口返回文案和兜底语言。
>
> 我会把语言、币种、日期、金额和枚举都作为可扩展配置，业务代码尽量不要写死中文或固定格式。

### Q4：权限按钮怎么封装？

答：

> 登录后后端返回权限码，前端存到 Store。按钮层可以用自定义指令 v-permission 或 PermissionButton 组件，根据权限码判断显示或禁用。
>
> 但这只负责用户体验，真正安全必须后端接口做权限校验。

### Q5：如何避免重复请求？

答：

> 可以从业务和技术两层处理。业务上避免页面重复 mounted 请求、切换 tab 重复请求；技术上可以做请求去重、AbortController 取消、按钮 loading 防重复提交、缓存相同查询条件的结果。

### Q6：如何处理接口字段经常变化？

答：

> 首先要推动接口文档和变更说明。前端代码上，我会用 TypeScript 类型约束、数据转换层和默认值兜底。页面不要直接深度依赖后端原始字段，尽量在 adapter 层转换成前端稳定模型。

### Q7：如何设计一个数据看板？

答：

> 我会先拆指标体系、数据来源、筛选条件、图表类型和刷新频率。前端架构上，把布局、图表配置、数据请求、指标计算和权限拆开。可拖拽看板可以用 Gridstack 管布局，用 ECharts 渲染图表，用配置描述图表类型和指标。

### Q8：如何做移动端多端适配？

答：

> 首先统一设计稿尺寸和布局方案，再处理不同平台 API、权限、样式、导航栏、安全区、文件上传、扫码、定位等差异。Uniapp 里可以用条件编译处理平台差异，同时通用逻辑尽量封装成组件和 hooks。

### Q9：如何判断一个功能该不该抽组件？

答：

> 如果它在多个页面重复出现，或者未来会持续变化，并且有稳定输入输出，就适合抽组件。如果只是一次性强业务逻辑，强行抽象可能增加理解成本。
>
> 我的原则是先复用，再抽象；抽象要有边界，不为了抽象而抽象。

### Q10：如果后端接口还没好，前端怎么推进？

答：

> 先和后端约定接口文档、字段、错误码和 Mock 数据。前端可以基于 Mock 并行开发页面、状态和交互。等接口完成后替换真实 API，再集中联调边界场景。

### 1. 自我定位

> 7 年高级前端，主攻 Vue / TypeScript / 工程化 / SaaS / 跨端 / 大屏。近两年用 AI 参与 Java 后端开发，优势是前端深度 + 后端理解 + 全链路闭环。

### 2. 项目主线

> 全房通 SaaS：房源、租客、账单、设备、看板，做核心模块、性能优化、Vuex 拆分、配置化看板、后端联调。
>
> 海外版：Vue3 + Vite + TS 从 0 到 1，做权限、请求、Pinia、组件规范、多语言、多币种。
>
> 移动端：Uniapp 重构，一套代码多端适配，封装移动端组件库，VitePress 文档沉淀。
>
> 大屏：9720×1920 超宽屏，vw/vh + 动态缩放 + ECharts + 视频图片优化。

### 3. 性能优化

> 先度量，再优化。工具看 Performance、Network、Lighthouse、Bundle Analyzer。手段是路由懒加载、组件按需加载、拆包、CDN、缓存、图片压缩、减少请求、keep-alive。结果是首屏 4.2s 到 2.1s，大屏 3s 到 1s。

### 4. Vue

> Vue2 defineProperty，Vue3 Proxy。Composition API 按业务逻辑组织，更适合复杂组件和复用。Pinia 比 Vuex 更轻，TS 支持更好。权限分菜单、路由、按钮、接口，后端必须兜底。

### 5. 工程化

> Vite 快是因为开发环境原生 ESM 按需加载，依赖预构建用 esbuild，生产构建走 Rollup。Webpack 老项目重点做拆包、缓存、按需加载和构建分析。规范要工具化，接 ESLint、Prettier、TS、提交检查、CI 和 AI Review。

### 6. Java 后端

> 主前端，不冒充纯后端。能理解 Controller / Service / Mapper 分层，能写业务接口、SQL、字段映射、异常处理、统一响应和联调。Spring Boot 流程是 Controller 接参，Service 业务，Mapper 查库，统一响应返回。

### 7. AI

> AI 用于需求拆解、代码生成、Bug 定位、重构、测试、文档。AI 是提效工具，不是能力替代。生成代码必须人工 Review，重点看业务、边界、权限、安全、性能和数据一致性。
