**回答：**
全房通是面向长租公寓、保租房、人才公寓、宿舍、写字楼和产业园区的 SaaS 管理平台，核心目标是帮助运营商完成房源、租客、合同、账单、智能设备和运营数据的全生命周期管理。前端技术栈主要是 Vue2、Webpack、Vuex、ElementUI、ECharts、Gridstack，后端是 Java Spring Boot、MySQL、Redis。

我主要负责核心业务模块开发、性能优化、可视化仪表盘、前后端协作规范以及部分后端接口开发。比较有代表性的成果是通过路由懒加载、组件按需加载、打包拆分、CDN 和缓存优化，把首屏加载从 4.2 秒降到 2.1 秒；同时参与接口聚合、慢查询分析和缓存策略，提升整体交互响应速度。

**速记关键词：**
公寓 SaaS、房源/租客/账单/设备、Vue2、Spring Boot、性能优化、仪表盘。

### 6. 这个项目中你最有挑战的点是什么？

**回答：**
最有挑战的是业务复杂度和性能问题叠加。公寓管理平台的业务链路比较长，比如房源、租客、合同、账单、设备之间有关联，一个页面往往要展示多类数据。如果前端直接堆接口、后端查询没有优化，就会导致首屏慢、交互卡、接口响应不稳定。

我的处理方式是先用数据定位瓶颈，比如看浏览器 Performance、Network、Webpack 构建结果、接口耗时和 SQL 执行计划。前端侧做路由懒加载、组件拆分、虚拟列表或分页、图表按需渲染；后端侧推动接口聚合、减少无效字段、优化 SQL 索引、对热点数据加 Redis 缓存。这个过程让我从单纯页面开发转向了全链路性能优化。

**速记关键词：**
复杂业务、数据关联、全链路定位、前端拆分、后端聚合、SQL/缓存。

### 7. 可拖拽可配置仪表盘怎么设计？

**回答：**
仪表盘的核心是“布局配置”和“组件配置”分离。布局层使用 Gridstack 管理卡片的位置、宽高、拖拽和缩放；业务组件层把每个卡片抽象成独立组件，比如出租率、空置房源、账单统计、设备状态。每个卡片都有唯一类型、配置参数、接口参数和展示组件。

保存时把布局信息和组件配置序列化成 JSON 存到后端；加载时后端返回配置，前端根据 type 动态渲染组件。这样运营人员可以自定义看板，开发侧也能通过新增组件类型扩展能力，不需要每次改整体页面。

**速记关键词：**
布局 JSON、组件 type、动态渲染、配置持久化、Gridstack。

Vue3/Vite/TS、国际化、多币种、配置化、海外业务规则。

### 9. 国际化方案怎么做？

**回答：**
国际化我会拆成三层：文案国际化、格式国际化和业务规则国际化。文案层用 i18n key 管理，不在页面里写死中文；格式层统一封装日期、金额、币种、数字格式；业务规则层把不同地区的字段、校验、账单规则抽成配置，而不是到处写 if else。

落地时会建立翻译 JSON 文件、命名规范、缺失 key 检查机制，并用 AI 辅助初版翻译和文案校对，但最终还是要人工审核，避免业务含义翻译错误。

**速记关键词：**
文案、格式、规则三层；key 管理；配置化；AI 翻译加人工审核。

### 10. Uniapp 跨端项目怎么保证多端一致？

**回答：**
跨端一致性主要靠架构约束和适配层。首先业务逻辑尽量放在公共层，页面和组件复用；其次对平台差异做统一封装，比如权限、文件上传、扫码、定位、设备能力调用都通过 adapter 层处理，不让业务页面直接写大量条件编译。

样式上会建立统一设计变量和组件规范，避免每个页面随意写。对于小程序、H5、Android、iOS、鸿蒙之间的差异，会通过条件编译解决平台特有问题，同时保留公共逻辑一致。测试时重点覆盖登录、权限、列表、表单、支付或账单等核心路径。

**速记关键词：**
公共业务层、adapter 适配层、条件编译、统一组件、核心路径测试。

### 12. 线上 Bug 率降低 35% 是怎么做到的？

**回答：**

质量前置、ESLint、AI Review、人工 Review、风险清单。

## 2. 前端基础高频题

### 13. Vue2 和 Vue3 响应式有什么区别？

**回答：**
Vue2 主要基于 Object.defineProperty 劫持对象属性，需要递归遍历，数组和新增属性有一些限制，所以要用 Vue.set 处理。Vue3 使用 Proxy，可以直接代理整个对象，对新增属性、删除属性、数组变化支持更自然，也更适合做性能优化和类型推导。

另外 Vue3 配合 Composition API，可以把同一业务逻辑聚合在一起，复用性更好；Vue2 的 Options API 更适合简单页面，但复杂业务里 data、methods、computed 分散，维护成本会变高。

**速记关键词：**
defineProperty vs Proxy；新增属性；数组；Composition API。

### 14. Composition API 的优势是什么？

**回答：**
Composition API 最大优势是逻辑复用和复杂业务组织。以前 Options API 会按 data、methods、computed 分类，业务复杂后同一个功能的逻辑分散在不同位置。Composition API 可以按业务功能组织代码，比如 useTenant、useBill、usePermission，把状态、方法、计算逻辑、请求逻辑放在一起。

在大型 SaaS 项目里，这种方式更利于组件拆分、逻辑复用和 TypeScript 类型推导，也更适合沉淀通用业务 hooks。

**速记关键词：**
按业务聚合、逻辑复用、TS 友好、适合大型项目。

### 15. Vue 中 key 的作用是什么？

**回答：**
key 是虚拟 DOM diff 时识别节点身份的标识。没有 key 或 key 不稳定时，Vue 可能复用错误的 DOM 节点，导致表单状态错乱、组件状态残留。列表渲染时应该使用稳定唯一的业务 id，而不是 index，特别是列表存在新增、删除、排序时。

**速记关键词：**
节点身份、diff、避免错误复用、不要随便用 index。

### 16. computed 和 watch 的区别？

**回答：**
computed 适合从已有状态推导新值，有缓存，依赖不变就不会重新计算，比如总价、筛选后的列表。watch 适合监听状态变化后执行副作用，比如请求接口、写缓存、埋点、手动同步某些状态。

简单记忆：要一个“值”用 computed，要“做一件事”用 watch。

**速记关键词：**
computed 是值，watch 是动作；缓存 vs 副作用。

### 17. Vue 性能优化你做过哪些？

**回答：**
我做过的优化包括路由懒加载、组件按需加载、第三方库按需引入、图片压缩和懒加载、Webpack/Vite 拆包、CDN、缓存策略、长列表分页或虚拟滚动、图表延迟渲染、避免重复请求、减少无意义响应式数据。

在全房通项目中，我通过这些手段把首屏从 4.2 秒优化到 2.1 秒。我的方法不是盲目优化，而是先用 Performance、Network、bundle analyzer 和接口耗时定位瓶颈，再针对性处理。

**速记关键词：**
先定位再优化；懒加载、拆包、CDN、缓存、虚拟列表、减少重复请求。

### 18. Webpack 和 Vite 的区别？

**回答：**
Webpack 是传统打包器，开发阶段也需要构建依赖图，项目大了启动和热更新会变慢。Vite 利用浏览器原生 ES Module，开发阶段按需编译源码，依赖预构建，所以启动和 HMR 更快；生产环境通常基于 Rollup 打包。

在海外版项目里，我用 Vite 结合依赖预构建、按需加载、拆包，把热更新从 2 到 3 秒优化到 200 毫秒以内。

**速记关键词：**
Webpack 全量构建；Vite ESM 按需编译；依赖预构建；HMR 快。

### 19. 前端如何做权限控制？

**回答：**
一般分成路由权限、菜单权限、按钮权限和接口权限。前端会根据后端返回的角色、权限码或菜单树动态生成路由和菜单；按钮通过权限指令或函数控制展示；接口请求带 token，并处理 401、403 等状态。

但真正的安全一定在后端，前端权限主要是体验和减少误操作，不能只靠前端隐藏按钮来保证安全。

**速记关键词：**
路由、菜单、按钮、接口；前端控制体验，后端保证安全。

### 20. 如何封装 axios 请求？

**回答：**
通常会封装统一实例，配置 baseURL、timeout、请求头；请求拦截器里加 token、traceId、公共参数；响应拦截器里统一处理业务 code、错误提示、登录过期、文件流、重复请求取消等。

还会把 API 按模块拆分，配合 TypeScript 定义请求参数和返回类型，减少字段错误。对于需要防重复提交的接口，可以加 loading 锁、请求去重或幂等 key。

**速记关键词：**
实例、请求拦截、响应拦截、错误统一、类型定义、防重复。

### 21. 前端如何处理大数据列表？

**回答：**
先看业务是否真的需要一次性展示大量数据。常规做法是分页、后端筛选、按需加载。如果必须展示很多行，可以使用虚拟列表，只渲染可视区域。还要避免复杂 computed 反复计算，减少深层响应式，表格列过多时可以做列懒渲染或固定区域优化。

**速记关键词：**
分页优先、后端筛选、虚拟列表、减少响应式和重复计算。

### 22. 前端怎么做首屏优化？

**回答：**
首屏优化可以从资源、渲染、接口三方面入手。资源上做路由懒加载、代码分割、压缩、CDN、图片优化；渲染上减少首屏组件数量，非关键组件延迟加载，骨架屏提升体验；接口上减少首屏请求数量，做接口聚合、缓存、并发控制和超时处理。

**速记关键词：**
资源小、渲染少、接口快；拆包、CDN、骨架屏、接口聚合。

### 23. TypeScript 给项目带来什么价值？

**回答：**
TypeScript 最大价值是把很多运行时错误提前到编译阶段，比如接口字段拼错、参数类型不对、组件 props 不匹配。对于多人协作和大型项目，类型本身也是文档，能提升可维护性和重构安全性。

在 Vue3 项目里，TS 配合接口类型、组件 props 类型、业务枚举、表单模型类型，可以显著减少字段联调问题。

**速记关键词：**
提前发现错误、类型即文档、重构安全、减少联调成本。

## 3. JavaScript 与浏览器高频题

### 24. 事件循环是什么？

**回答：**
JavaScript 是单线程执行的，但浏览器提供了异步能力。同步代码先进入调用栈执行，异步任务完成后进入任务队列。事件循环会不断检查调用栈是否为空，然后执行微任务和宏任务。常见微任务有 Promise.then、MutationObserver，宏任务有 setTimeout、setInterval、事件回调、网络回调。

执行顺序可以简单记为：同步代码先执行，当前宏任务结束后清空微任务，再执行下一个宏任务。

**速记关键词：**
同步、微任务、宏任务；Promise 先于 setTimeout。

### 25. 防抖和节流区别？

**回答：**
防抖是频繁触发时只执行最后一次，适合搜索输入、窗口 resize 后计算。节流是固定时间内最多执行一次，适合滚动监听、拖拽、按钮连续点击限制。

简单记忆：防抖等你停下来再执行，节流按固定节奏执行。

**速记关键词：**
防抖最后一次；节流固定频率。

### 26. 深拷贝和浅拷贝区别？

**回答：**
浅拷贝只复制第一层，里面的对象还是共享引用；深拷贝会递归复制所有层级，修改新对象不会影响原对象。项目里不能盲目深拷贝，因为大对象深拷贝会影响性能。简单数据可以用 structuredClone，复杂场景要注意函数、Date、Map、循环引用等。

**速记关键词：**
引用共享 vs 完全复制；注意性能和特殊类型。

### 27. 闭包是什么？有什么风险？

**回答：**
闭包是函数能够访问它定义时的外部作用域变量，即使外部函数已经执行完。它常用于封装私有变量、函数工厂、防抖节流等。风险是如果闭包长期持有大对象或 DOM 引用，可能导致内存无法释放。

**速记关键词：**
访问外部变量、私有状态、可能内存泄漏。

### 28. 浏览器缓存有哪些？

**回答：**
主要分强缓存和协商缓存。强缓存通过 Cache-Control、Expires 控制，命中时不请求服务器；协商缓存通过 ETag、Last-Modified 判断资源是否变化，没变化返回 304。项目中静态资源通常用 hash 文件名配合长期强缓存，HTML 不做强缓存或设置较短缓存，保证发版后能加载最新资源。

**速记关键词：**
强缓存不请求；协商缓存 304；静态资源 hash，HTML 短缓存。

### 29. 跨域是什么？怎么解决？

**回答：**
跨域是浏览器同源策略限制，不同协议、域名、端口之间的请求会被限制。常见解决方式有后端配置 CORS、开发环境代理、Nginx 反向代理、JSONP。现在项目里最常用的是 CORS 和代理。

需要注意跨域是浏览器限制，不是服务器之间不能通信。

**速记关键词：**
协议域名端口；CORS；代理；浏览器限制。

### 30. 前端内存泄漏常见场景？

**回答：**
常见场景有定时器没清理、事件监听没移除、WebSocket 没关闭、闭包长期持有大对象、组件销毁后异步回调还在 setState、第三方图表实例没 dispose。解决方式是在组件卸载时清理资源，封装 hooks 或组件时统一处理生命周期。

**速记关键词：**
定时器、事件、Socket、图表、异步回调；卸载清理。

## 4. React 高频题

### 31. React 和 Vue 的核心差异？

**回答：**
Vue 更偏模板和响应式系统，开发体验上约束更多，上手快；React 更偏函数式和状态驱动，JSX 表达能力强，灵活度高。Vue 的依赖追踪更自动，React 的更新更多依赖状态变化和重新渲染机制。

在项目选择上，我会根据团队技术栈、业务复杂度、生态和维护成本来选，不会简单说谁更好。

**速记关键词：**
Vue 模板响应式；React JSX 状态驱动；看团队和业务。

### 32. React hooks 为什么不能写在条件语句里？

**回答：**
React 依赖 hooks 的调用顺序来关联状态。如果 hooks 写在条件语句或循环里，每次渲染调用顺序可能不同，React 就无法正确匹配 useState、useEffect 等状态，导致状态错乱。所以 hooks 必须写在组件顶层。

**速记关键词：**
调用顺序稳定；顶层调用。

### 33. useEffect 常见用途和注意点？

**回答：**
useEffect 用来处理副作用，比如请求数据、订阅事件、设置定时器、操作外部资源。注意点是依赖数组要准确，否则可能出现重复请求或闭包拿到旧值；如果 effect 里注册了事件、定时器、订阅，需要在 return 中清理。

**速记关键词：**
副作用、依赖数组、清理函数、避免旧闭包。

## 5. 后端 Java Spring Boot 高频题

### 34. Spring Boot 的核心优势是什么？

**回答：**
Spring Boot 主要优势是约定优于配置、自动配置和快速启动项目。它把 Spring 常用配置封装好了，开发者通过 starter 依赖就能快速集成 Web、MyBatis、Redis、Validation 等能力，减少大量 XML 和样板配置。

在业务开发中，我们更多关注 Controller、Service、Mapper、实体类、配置文件和业务逻辑，不需要从零搭建底层框架。

**速记关键词：**
自动配置、starter、约定优于配置、快速开发。

### 35. Controller、Service、Mapper 分别做什么？

**回答：**
Controller 负责接收请求、参数校验、返回统一响应；Service 负责业务逻辑、事务控制、调用多个数据操作；Mapper 或 DAO 负责数据库访问和 SQL 映射。

分层的好处是职责清晰，方便测试、维护和复用。不要把大量业务逻辑写在 Controller，也不要让 Mapper 处理复杂业务判断。

**速记关键词：**
Controller 接口；Service 业务；Mapper 数据；职责分离。

### 36. Spring Boot 一个接口开发流程是什么？

**回答：**
我一般先确认需求和字段，设计请求参数、返回结构、错误码；然后看是否需要建表或改表；接着写实体类、DTO、VO、Mapper、Service、Controller；补充参数校验、权限校验、事务；最后用接口工具和前端联调，检查异常场景和边界条件。

如果使用 AI，我会让 AI 生成初版样板代码和测试用例，但会自己检查 SQL、权限、事务、空值和业务边界。

**速记关键词：**
需求字段、表结构、DTO/VO、Service、Controller、校验、联调。

### 37. 什么是依赖注入？

**回答：**
依赖注入就是对象不自己 new 依赖，而是由 Spring 容器创建和管理，再注入到需要的类里。这样可以降低耦合，方便替换实现和测试。常见方式有构造器注入、字段注入、setter 注入，实际项目更推荐构造器注入，因为依赖更明确，也方便单元测试。

**速记关键词：**
Spring 管对象；降低耦合；推荐构造器注入。

### 38. @Transactional 有什么作用？什么时候会失效？

**回答：**
@Transactional 用来保证一组数据库操作要么全部成功，要么全部回滚。常用于创建订单、账单结算、批量更新等场景。它可能在几种情况下失效：方法不是 public、同类内部方法直接调用、异常被 try catch 吞掉没有抛出、默认只回滚 RuntimeException、数据库引擎不支持事务。

**速记关键词：**
事务一致性；public；避免内部调用；异常要抛出；默认运行时异常回滚。

### 39. GET 和 POST 的区别？

**回答：**
GET 通常用于查询，参数放在 URL，适合幂等请求，可以被缓存；POST 通常用于新增或提交复杂数据，参数放在请求体，不适合被缓存。严格来说 GET/POST 本身不是安全边界，安全要靠 HTTPS、鉴权、权限校验和后端规则。

**速记关键词：**
GET 查询幂等；POST 提交数据；安全靠鉴权和 HTTPS。

### 40. 如何设计统一返回结构？

**回答：**
一般会包含 code、message、data、traceId 等字段。code 表示业务状态，message 给前端或用户提示，data 是业务数据，traceId 方便排查日志。分页数据可以统一包含 list、total、pageNum、pageSize。

统一返回结构的好处是前端拦截器能统一处理错误、登录过期、权限不足和提示逻辑。

**速记关键词：**
code/message/data/traceId；分页 list/total；前端统一处理。

### 41. 如何做参数校验？

**回答：**
Spring Boot 中常用 Validation 注解，比如 @NotNull、@NotBlank、@Size、@Min、@Max、@Pattern。Controller 参数上加 @Valid 或 @Validated，配合全局异常处理返回统一错误信息。

复杂业务校验不能只靠注解，比如账单金额、日期范围、状态流转，需要在 Service 里根据业务规则校验。

**速记关键词：**
Validation 注解；全局异常；复杂规则放 Service。

### 42. 全局异常处理怎么做？

**回答：**
可以用 @RestControllerAdvice 和 @ExceptionHandler 统一捕获异常，比如参数校验异常、业务异常、权限异常、系统异常。然后转换成统一返回结构，避免把堆栈信息直接暴露给前端。

同时日志里要记录 traceId、请求路径、用户信息和异常堆栈，方便线上排查。

**速记关键词：**
RestControllerAdvice；ExceptionHandler；统一响应；日志 traceId。

### 43. 什么是幂等？怎么保证？

**回答：**
幂等是同一个请求执行一次和多次结果一致。查询天然幂等，但新增、支付、账单生成、批量提交这类操作要特别处理。常见方案有唯一索引、防重复提交 token、Redis 分布式锁、业务状态机、请求流水号。

比如账单生成可以用房间、租客、账期建立唯一约束，重复请求时不会重复生成账单。

**速记关键词：**
多次执行结果一致；唯一索引、token、Redis 锁、状态机。

### 44. 如何防止接口重复提交？

**回答：**
前端可以做按钮 loading、防抖、请求锁；后端要做真正保障，比如唯一索引、幂等 token、业务流水号、Redis 锁。因为前端限制可以被绕过，所以关键业务必须以后端幂等为准。

**速记关键词：**
前端拦体验，后端保安全；唯一索引/Redis/token。

## 6. MySQL 高频题

### 45. MySQL 索引是什么？为什么能加速查询？

**回答：**
索引可以理解为数据库给某些字段建立的目录。没有索引时可能要全表扫描，有索引时可以通过 B+Tree 快速定位数据。MySQL InnoDB 常用 B+Tree 索引，因为它适合范围查询、排序和磁盘 IO 优化。

但索引不是越多越好，索引会占空间，也会降低新增、更新、删除的速度，因为数据变化时索引也要维护。

**速记关键词：**
目录、B+Tree、减少全表扫描；不是越多越好。

### 46. 联合索引最左前缀原则是什么？

**回答：**
如果建立联合索引 `(a, b, c)`，查询条件要从最左边的 a 开始连续使用，才能更好命中索引。比如 where a = ? and b = ? 可以用，where b = ? 通常不能充分使用这个联合索引。

设计联合索引时，要把区分度高、常用于筛选和排序的字段结合查询场景来安排顺序。

**速记关键词：**
从左到右连续命中；结合查询场景设计。

### 47. 什么情况下索引会失效？

**回答：**
常见情况有对索引列使用函数或计算、like 以通配符开头、隐式类型转换、or 条件使用不当、不符合最左前缀原则、范围查询后面的列无法充分利用索引。实际项目里要用 explain 看执行计划，而不是凭感觉判断。

**速记关键词：**
函数、计算、左模糊、类型转换、or、最左前缀、explain。

### 48. 你怎么排查慢 SQL？

**回答：**
先确认慢 SQL 来源，比如接口耗时日志、慢查询日志、APM 或数据库监控；然后用 explain 看是否走索引、扫描行数、join 类型、排序和临时表；再结合业务优化，比如加合适索引、减少返回字段、分页优化、拆分复杂查询、避免循环查库、必要时加缓存。

在 SaaS 项目里，我会特别关注房源、账单、租客这类高频列表的筛选条件和分页查询。

**速记关键词：**
定位 SQL、explain、索引、字段、分页、缓存、避免循环查库。

### 49. 分页查询深分页怎么优化？

**回答：**
传统 limit offset 在 offset 很大时会扫描和丢弃大量数据，性能会下降。优化方式包括基于游标分页，比如 where id > lastId limit n；或者先查索引 id，再回表查详情；业务上也可以限制最大页数，避免用户无限翻页。

**速记关键词：**
offset 大会慢；游标分页；先查 id 再回表；限制最大页。

### 50. 数据库事务 ACID 是什么？

**回答：**
ACID 分别是原子性、一致性、隔离性、持久性。原子性表示事务内操作要么全成功要么全失败；一致性表示事务前后数据符合业务规则；隔离性表示并发事务之间互不干扰；持久性表示提交后数据不会丢失。

**速记关键词：**
全成功或全失败、规则正确、并发隔离、提交持久。

### 51. MySQL 常见隔离级别？

**回答：**
常见隔离级别有读未提交、读已提交、可重复读、串行化。MySQL InnoDB 默认是可重复读。隔离级别越高，并发问题越少，但性能成本越高。实际业务中要根据一致性要求选择，不能只追求最高隔离级别。

**速记关键词：**
RU、RC、RR、Serializable；InnoDB 默认 RR；一致性和性能权衡。

## 7. Redis 高频题

### 52. Redis 在项目里用来做什么？

**回答：**
Redis 常用于缓存热点数据、验证码、登录 token、分布式锁、限流、排行榜、临时状态等。在 SaaS 系统里，我更常见的使用是缓存字典、权限、配置、热点统计数据，减少数据库压力。

**速记关键词：**
缓存、token、锁、限流、热点数据。

### 53. 缓存穿透、击穿、雪崩是什么？

**回答：**
缓存穿透是查询一个缓存和数据库都不存在的数据，导致请求一直打到数据库，可以用空值缓存、布隆过滤器、参数校验解决。缓存击穿是某个热点 key 过期，大量请求同时打到数据库，可以用互斥锁、热点 key 不过期、提前刷新解决。缓存雪崩是大量 key 同时过期或 Redis 故障，导致数据库压力暴增，可以用过期时间随机化、多级缓存、限流降级解决。

**速记关键词：**
穿透查不存在；击穿热点过期；雪崩大量过期；空值/锁/随机过期。

### 54. Redis 和 MySQL 数据一致性怎么处理？

**回答：**
常见策略是先更新数据库，再删除缓存，而不是直接更新缓存。因为数据库是最终数据源，删除缓存后下次查询再加载新数据。为了降低并发下的不一致，可以使用延迟双删、消息队列重试、设置合理过期时间。

对一致性要求非常高的业务，不能只依赖缓存，要以数据库事务和业务校验为准。

**速记关键词：**
先更新 DB，再删缓存；延迟双删；过期兜底；DB 为准。

### 55. Redis 分布式锁要注意什么？

**回答：**
要注意加锁原子性、锁过期时间、锁 value 唯一、释放锁时只能释放自己的锁。常用 set key value nx ex 实现基础锁，释放时用 Lua 脚本判断 value 后删除，避免误删别人持有的锁。复杂场景可以使用 Redisson。

**速记关键词：**
NX EX、唯一 value、Lua 删除、避免误删、Redisson。

## 8. 前后端协作与接口设计

### 56. 你如何制定前后端协作规范？

**回答：**
我会从接口路径、请求方法、参数命名、返回结构、错误码、分页格式、权限规则、字段类型、时间格式、文件上传、联调流程几个方面统一规范。比如统一返回 code/message/data，分页统一 list/total/pageNum/pageSize，时间统一 ISO 或时间戳，金额用分或 Decimal 避免精度问题。

规范的价值是减少沟通成本和联调问题，尤其是多人协作时，大家按同一套标准开发，前端拦截器和后端异常处理也能统一。

**速记关键词：**
路径、方法、参数、返回、错误码、分页、时间、金额、权限。

### 57. 接口字段前后端不一致怎么解决？

**回答：**
短期可以通过适配层处理，比如前端 mapper 或后端 VO 转换；长期应该推动接口契约明确，比如接口文档、TypeScript 类型、Mock 数据、字段变更记录。如果字段频繁变化，要在需求评审阶段确认字段含义、类型、是否必填、默认值和兼容策略。

**速记关键词：**
短期适配，长期契约；文档、类型、Mock、变更记录。

### 58. 如何设计一个列表查询接口？

**回答：**
要考虑筛选条件、分页、排序、权限范围、返回字段和性能。请求参数一般包含 pageNum、pageSize、关键词、状态、时间范围等；返回 list、total、分页信息。后端要避免返回无用大字段，SQL 要根据高频筛选条件设计索引，权限条件要在后端控制。

**速记关键词：**
筛选、分页、排序、权限、字段、索引。

### 59. 金额字段如何处理？

**回答：**
金额不能用 JavaScript 浮点数随意计算，容易出现精度问题。前端展示可以格式化，计算尽量用整数分或 decimal 库；后端 Java 可以用 BigDecimal；数据库用 DECIMAL 类型。前后端要约定单位，比如接口传分还是元，避免混乱。

**速记关键词：**
不用浮点乱算；前端整数分/decimal；后端 BigDecimal；DB DECIMAL。

### 60. 时间和时区怎么处理？

**回答：**
国内单地区系统可以统一后端存储和返回标准格式，比如 yyyy-MM-dd HH:mm:ss；海外系统更要注意时区，建议数据库存 UTC 或明确时区，接口返回 ISO 时间或时间戳，前端根据用户地区格式化展示。关键是前后端约定清楚，不能每个页面自己处理。

**速记关键词：**
统一存储、统一返回、前端格式化、海外注意时区。

## 9. 系统设计与业务场景题

### 61. 如果让你设计房源管理模块，你怎么做？

**回答：**
我会先拆实体：楼宇、楼层、房间、房型、租客、合同、账单、设备。房源表保存房间基础信息、状态、面积、租金、所属楼宇楼层；合同关联租客和房间；账单关联合同和账期；设备关联房间。

接口上包括房源列表、详情、新增编辑、状态变更、导入导出、房源绑定设备、房态统计。性能上房源列表通常高频使用，要做好筛选索引、分页查询和字典缓存。权限上不同运营商、门店、角色只能看自己的房源范围。

**速记关键词：**
实体拆分、列表详情、状态流转、分页索引、权限范围。

### 62. 如果让你设计账单模块，你怎么做？

**回答：**
账单模块核心是准确性和幂等。实体包括账单、账单明细、租客、合同、房间、支付记录。生成账单时要根据合同周期、租金、押金、水电费、优惠规则计算。要避免重复生成，可以用租客、合同、账期、费用类型做唯一约束或幂等 key。

状态上可以设计为待支付、部分支付、已支付、已逾期、已作废。涉及金额必须用 BigDecimal 和 DECIMAL，操作要有日志，关键流程加事务。

**速记关键词：**
准确、幂等、唯一约束、状态机、BigDecimal、事务日志。

### 63. 如果一个页面加载慢，你怎么排查？

**回答：**
我会按链路排查：先看 Network 是资源慢还是接口慢；如果资源慢，看包体积、缓存、CDN、图片；如果接口慢，看接口耗时、SQL、Redis、是否请求过多；如果渲染慢，看 Performance、组件数量、长列表、图表渲染、重复计算。

定位后再优化，不会一上来就改代码。比如首屏慢可能是包太大，也可能是接口串行，也可能是图表一次性渲染太多。

**速记关键词：**
资源、接口、渲染三段；Network、Performance、SQL。

### 64. 如果接口偶发超时，你怎么排查？

**回答：**
先确认是前端网络、网关、后端服务还是数据库问题。看请求耗时、后端日志、traceId、数据库慢查询、Redis 连接、线程池和外部服务依赖。如果是某些参数才慢，可能是 SQL 没走索引；如果高峰期慢，可能是并发、连接池或缓存问题。

处理上可以优化 SQL、加索引、加缓存、接口拆分或聚合、超时重试、降级提示。

**速记关键词：**
traceId、日志、慢 SQL、连接池、缓存、高峰期、参数差异。

### 65. 如何设计一个可配置 JSON 表单？

**回答：**
核心是用 JSON 描述字段，再由渲染器动态生成表单。每个字段配置 type、label、prop、defaultValue、rules、options、visible、disabled、componentProps 等。渲染器根据 type 映射到输入框、选择器、日期、上传等组件。

复杂场景要支持联动，比如选择房源后加载租客，选择费用类型后改变校验规则。保存时可以输出标准表单数据。这样能减少重复页面开发，适合中后台配置类场景。

**速记关键词：**
schema、字段配置、组件映射、校验、联动、动态渲染。

### 66. 如何保证项目可维护性？

**回答：**
我会从目录结构、命名规范、组件拆分、接口封装、类型定义、代码规范、文档和 Review 入手。复杂业务不要把所有逻辑堆在一个页面里，要拆成业务组件、hooks、service、utils。公共逻辑沉淀成组件库或工具函数，接口和类型集中管理。

团队层面要有 ESLint、Prettier、提交规范、代码评审和技术文档，降低新人接手成本。

**速记关键词：**
拆分、封装、类型、规范、文档、Review。

## 10. AI 全栈岗位专项题

### 67. AI 编程工具会不会生成不可靠代码？你怎么控制？

**回答：**
会，所以我把 AI 当成助手，不当成最终决策者。控制方式包括明确 prompt、限制修改范围、让 AI 先给方案再生成代码、对关键逻辑人工 review、补充单元测试和边界测试、检查安全问题、用 lint 和类型检查兜底。

对于后端代码，我会重点检查权限、事务、SQL、空指针、异常处理、幂等和数据一致性。

**速记关键词：**
AI 是助手；人工负责；Review、测试、lint、权限事务 SQL。

### 68. 你如何用 AI 提升团队效率？

**速记关键词：**
模板化、标准化、上下文、减少重复劳动。

### 69. AI 生成代码后你会检查哪些点？

**回答：**
前端检查组件状态、边界空值、接口字段、性能、样式兼容、权限展示；后端检查参数校验、权限校验、事务、SQL 是否安全、是否可能 N+1 查询、异常是否统一处理、是否有幂等问题；整体还要跑 lint、类型检查、测试和本地联调。

**速记关键词：**
空值、权限、事务、SQL、异常、幂等、测试。

### 70. 你怎么看 AI 对开发岗位的影响？

**回答：**
AI 会减少重复编码，但不会替代业务理解、架构判断、质量控制和沟通协作。未来开发者的价值会更多体现在能不能把业务拆清楚、把系统设计好、把 AI 结果审好，并且保证上线质量。

我的定位是把 AI 当作研发提效工具，让自己从单点编码者变成更能负责完整交付的人。

**速记关键词：**
减少重复编码；开发者负责业务、架构、质量、交付。

## 13. 面试前 30 分钟速背版

### 自我定位

我是 7 年前端背景的 AI 全栈开发，前端强项是 Vue/React/Uniapp、工程化、性能优化和复杂业务落地；后端能用 Spring Boot、MySQL、Redis 完成常规接口、SQL、缓存和联调；AI 工具能提升需求拆解、代码生成、测试和文档效率。

### 项目主线

全房通国内版：Vue2 + Webpack + ElementUI + Spring Boot，重点讲 SaaS、公寓管理、首屏 4.2 秒到 2.1 秒、Gridstack 仪表盘、前后端规范。

海外版：Vue3 + Vite + Pinia + TypeScript，重点讲从零搭架子、国际化、多币种、Vite HMR 从 2 到 3 秒到 200ms。

移动端：Uniapp + Vue3 + Pinia，重点讲一套代码多端适配、组件库、JSON 表单、VitePress 文档、跨端兼容。

### 前端必背

Vue2 defineProperty，Vue3 Proxy。

computed 是值，watch 是动作。

key 是节点身份，不建议用 index。

首屏优化看资源、接口、渲染。

Vite 开发快是因为 ESM 按需编译和依赖预构建。

权限分路由、菜单、按钮、接口，真正安全在后端。

### 后端必背

Controller 接请求，Service 写业务，Mapper 查数据库。

Spring Boot 优势是自动配置、starter、约定优于配置。

事务失效常见原因：非 public、同类内部调用、异常被吞、默认只回滚运行时异常。

统一返回结构：code、message、data、traceId。

幂等方案：唯一索引、token、Redis 锁、状态机、流水号。

### MySQL/Redis 必背

索引是目录，InnoDB 常用 B+Tree。

联合索引遵循最左前缀。

慢 SQL 用 explain，看索引、扫描行数、排序、临时表。

Redis 穿透查不存在，击穿热点 key 过期，雪崩大量 key 同时过期。

缓存一致性常用先更新数据库，再删除缓存。

### AI 必背

AI 用于需求拆解、代码生成、测试补充、日志分析、文档生成。

AI 代码不能直接上线，要检查权限、事务、SQL、异常、空值、幂等、性能和测试。

AI 替代重复编码，但不能替代业务理解、架构判断和质量责任。

## 14. 最容易被追问的 10 个问题

### 4. 你做后端时最怕什么问题？

**短答：**

### 5. 你如何处理复杂业务需求？

### 7. 你怎么看低代码或配置化？

**短答：**
配置化适合表单、列表、看板、流程这种规则相对稳定但字段变化频繁的场景。核心是 schema 设计、动态渲染、校验联动和扩展机制。不能所有东西都低代码，复杂强业务逻辑还是代码更清晰。

### 8. 你如何保证跨端质量？

**短答：**
公共逻辑统一，平台差异走 adapter，样式用统一规范，条件编译只处理平台特性。测试重点放在登录、权限、列表、表单、上传、扫码、账单等核心链路。

## 15. 一句话背诵卡

Vue3 比 Vue2 的响应式更强，核心是 Proxy 能代理整个对象。

Composition API 的价值是按业务组织逻辑，而不是按选项分散逻辑。

首屏优化先看资源、接口、渲染，不要盲目改代码。

Webpack 是传统打包器，Vite 开发阶段基于 ESM 按需编译，所以更快。

前端权限负责体验，真正安全必须靠后端校验。

Spring Boot 的核心是自动配置、starter 和约定优于配置。

Controller 管请求，Service 管业务，Mapper 管数据。

事务常见失效原因是同类内部调用、异常被吞、方法非 public。

索引像目录，能减少扫描，但会增加写入维护成本。

联合索引遵循最左前缀原则。

慢 SQL 要用 explain 看执行计划。

Redis 穿透是查不存在，击穿是热点过期，雪崩是大量过期。

缓存一致性常用先更新数据库，再删除缓存。

幂等就是同一请求执行多次结果一致。

AI 能提升效率，但质量责任必须由开发者承担。

我的优势是前端深、业务强、能全链路排查，并能用 AI 提升交付效率。
